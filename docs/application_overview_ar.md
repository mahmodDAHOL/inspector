# الجمهورية العربية السورية — وزارة الإعلام — مديرية الرقابة والتفتيش

> هذا الملف يوثّق **الوضع الفعلي الحالي للكود** (as-built) بعد جولة تحصين أمني كاملة، وليس تصورًا تخطيطيًا. كل ما هو مذكور هنا تم التحقق منه مباشرة من الكود المصدري ومن تشغيل النظام فعليًا داخل حاويات Docker بتاريخ 2026-08-28.

## ١. ما هو التطبيق؟

بوابة إلكترونية داخلية لمديرية الرقابة والتفتيش لإدارة **شكاوى الفساد والمخالفات الإدارية**: استقبال الشكوى، تحقيقها، تصعيدها عند الحاجة، إغلاقها، وتوقيعها رقميًا — مع لوحة تحكم للمدير لإدارة المستخدمين والإدارات، تقارير إحصائية، وسجل تدقيق شامل لكل نشاط في النظام.

## ٢. المكوّنات الرئيسية (Components)

النظام مبني على ٥ خدمات تعمل كحاويات Docker منفصلة (`docker-compose.yml`):

| الخدمة | الدور |
|---|---|
| `nginx` | البوابة الأمامية، تشفير TLS (HTTPS)، رؤوس أمان (HSTS/CSP)، توجيه الطلبات |
| `frontend` | تطبيق الواجهة (Vue 3) — بناء ثابت يُقدَّم عبر nginx داخلي |
| `backend` | واجهة برمجية (FastAPI) تحوي كل منطق الأعمال |
| `db` | قاعدة بيانات PostgreSQL 16 |
| `redis` | Redis 7 — يُستخدم فعليًا الآن لتحديد معدل الطلبات (Rate Limiting) |

### هيكلية الكود (بعد التحصين)

```
backend/app/
  api/v1/        # auth, complaints, users, departments, dashboard, reports, audit, external
  core/
    security.py      # كلمات المرور (Argon2)، JWT، TOTP، قوة كلمة المرور
    encryption.py     # تشفير الحقول (AES-256-GCM)
    signing.py         # توقيع رقمي حقيقي (RSA-PSS/SHA-384)
    deps.py             # get_current_user / require_roles
    rate_limit.py        # تحديد معدل الطلبات عبر Redis
    activity_log.py       # سجل النشاط العام
    log_chain.py            # سلسلة التجزئة (Hash Chain) لسجلات النشاط
    config.py                 # إعدادات صارمة (ترفض الأسرار الضعيفة/الافتراضية)
  models/         # User, Complaint, Department, ComplaintLog, ActivityLog
  db/session.py
  main.py

frontend/src/
  views/, components/, stores/, locales/ (ar.json/en.json), router.js
```

## ٤. المميزات الرئيسية (Features)

1. **إدارة الشكاوى** مع سير عمل محدد بدقة (انظر القسم ٦).
2. **الأدوار مُنفَّذة فعليًا على مستوى الخادم**: `viewer` قراءة فقط، `inspector` فما فوق يكتب، `senior_inspector` فما فوق فقط يوقّع — وليس مجرد وصف في الواجهة.
3. **الملاحظات السرّية محمية فعليًا**: ملاحظة معلّمة "سرّية" لا يراها إلا `senior_inspector` فما فوق أو من كتبها.
4. **توقيع رقمي حقيقي** — مفتاح RSA-2048 خاص بالنظام، توقيع RSA-PSS/SHA-384 فعلي لمحتوى التقرير، محفوظ في `digital_signatures` مع بصمة الشهادة، ويتطلب **إعادة تأكيد الهوية عبر رمز TOTP الحالي** (وليس رمز PIN ثابت).
5. **سجل نشاط لكل شكوى + سجل نشاط عام للنظام** — كلاهما **محصّن ضد التلاعب**: سلسلة تجزئة (Hash Chain) + Trigger في قاعدة البيانات يرفض أي `UPDATE`/`DELETE` حتى لمالك الجدول.
6. **لوحة تحكم (Dashboard)** بمؤشرات زمن الاستجابة (نسبة الاستجابة، متوسط الوقت، المعلّقة).
7. **تقارير** قابلة للتوليد ضمن مدى زمني، مع تنزيل JSON.
8. **لوحة تحكم إدارية** كاملة: المستخدمون (CRUD + كلمة مرور قوية إلزاميًا)، الأدوار (مرجعي)، الإدارات (CRUD)، نظرة عامة على النظام.
9. **مصادقة ثنائية العامل (MFA)** إلزامية — انظر القسم ٧.
10. **قفل الحساب** بعد ٥ محاولات فاشلة (١٥ دقيقة) + **تحديد معدل طلبات على مستوى IP** (١٥ محاولة/دقيقة) مستقل عن قفل الحساب، لمنع هجمات Credential Spraying.
11. **تكامل MediaGate الخارجي محمي فعليًا**: مفتاح API + توقيع HMAC لكل طلب، ومحدود بمعدل ٣٠ طلب/دقيقة لكل IP.
12. **دعم لغتين وواجهة RTL/LTR**، وضع داكن/فاتح، قائمة جانبية موحدة في كل الصفحات.

## ٥. آلية العمل العامة (Request Flow)

```
المتصفح ──HTTPS(443, TLS1.3)──> nginx (HSTS + CSP + رؤوس أمان) ──┬── "/"     ──> frontend
                                                                    └── "/api/" ──> backend

عند كل طلب API:
  axios يرفق Authorization: Bearer <access_token> تلقائيًا
       │
       ▼
  TrustedHostMiddleware — يرفض أي Host غير مُعرَّف في ALLOWED_HOSTS
       │
       ▼
  CORSMiddleware — يسمح فقط بالأصول المُعرَّفة في ALLOWED_ORIGINS (لا نجمة *)
       │
       ▼
  get_current_user — يفك تشفير JWT (HS256 فقط)، يتحقق من نشاط الحساب
       │
       ▼
  require_roles(...) عند الحاجة — 403 عند عدم توافق الدور
       │
       ▼
  منطق المسار ← SQLAlchemy AsyncSession ← PostgreSQL
```

**مصفوفة الصلاحيات المُنفَّذة فعليًا على وحدة الشكاوى:**

| الإجراء | الأدوار المسموحة |
|---|---|
| قراءة الشكاوى/السجل | أي مستخدم مسجّل دخول (بما فيهم `viewer`) |
| إنشاء / تغيير حالة / تعيين / تصعيد / إضافة ملاحظة | `inspector`, `senior_inspector`, `admin`, `super_admin` |
| توقيع التقرير | `senior_inspector`, `admin`, `super_admin` فقط |
| إدارة المستخدمين / الإدارات (كتابة) | `admin`, `super_admin` فقط |

## ٦. سير عمل الشكوى (Complaint Workflow)

```
إنشاء ──> received ──┬──> under_investigation ──┬──> closed (نهائي)
                      └──> closed                ├──> escalated ──┬──> under_investigation
                                                   └──> received     └──> closed
```
- الانتقالات مضبوطة بجدول صريح (`VALID_STATUS_TRANSITIONS`)، مُختبَر بوحدات pytest.
- `/escalate` إجراء منفصل: حالة → `escalated` + أولوية → `urgent` معًا.
- أول إجراء فعلي (تغيير حالة/تعيين/ملاحظة) يُسجَّل تلقائيًا كـ"أول استجابة" (`first_response_at`) — أساس مؤشرات زمن الاستجابة.
- كل إجراء يُنشئ سطرًا في سجل نشاط الشكوى (مُحصَّن ضد التلاعب، انظر القسم ٩).

## ٧. تسجيل الدخول ورمز التحقق (Login & MFA)

خطوتان إجباريتان:

### الخطوة ١ — `POST /api/v1/auth/login`
- تحقق من وجود الحساب، نشاطه، وعدم كونه مقفلاً (`locked_until`).
- كلمة المرور تُقارَن عبر **Argon2**.
- عند الفشل: عدّاد `failed_login_attempts` يزداد، ويُقفل الحساب تلقائيًا لمدة **١٥ دقيقة** بعد **٥** محاولات.
- محدود أيضًا بـ **١٥ طلب/دقيقة لكل IP** (مستقل عن قفل الحساب — يمنع تجربة حسابات كثيرة من نفس المصدر).
- عند النجاح: `temp_token` (٥ دقائق، `type: temp`) فقط — لا يمنح أي وصول.

### الخطوة ٢ — `POST /api/v1/auth/verify-totp`
- رمز ٦ أرقام من تطبيق مصادقة، يتغيّر كل ٣٠ ثانية (معيار **TOTP / RFC 6238** عبر `pyotp`).
- سرّ TOTP **مُخزَّن مشفّرًا** ولا يُفك إلا لحظة التحقق.
- **تم اكتشاف وإصلاح ثغرة حرجة هنا (٢٠٢٦-٠٨-٢٨):** كانت دالة المسار نفسها تحمل نفس اسم دالة التحقق المستوردة (`verify_totp`)، مما كان يجعل أي رمز — حتى الخاطئ تمامًا — يُقبل دائمًا. تم اكتشافها عبر اختبار pytest جديد، وتم إصلاحها وتأكيد الإصلاح حيًّا (رمز خاطئ يُرفض الآن بـ 401 كما يجب).
- محدود بـ ١٥ طلب/دقيقة لكل IP أيضًا.
- عند النجاح: `access_token` (١٥ دقيقة) + `refresh_token` (٧ أيام)، ويُحدَّث `last_login_at` ويُسجَّل الدخول في سجل النشاط العام.

### الرموز — ملخص
| الرمز | الصلاحية | ملاحظة |
|---|---|---|
| `temp_token` | ٥ دقائق | خطوة كلمة المرور فقط |
| `access_token` | ١٥ دقيقة | JWT/HS256، يحمل الدور |
| `refresh_token` | ٧ أيام | `POST /auth/refresh` يأخذه كجسم JSON (`{"refresh_token": "..."}`)، ويعيد قراءة الدور من قاعدة البيانات مباشرة بدل الوثوق بادعاء قديم |

## ٨. التوقيع الرقمي (Digital Signature)

`POST /complaints/{id}/sign` — يتطلب دورًا من `senior_inspector` فما فوق، وشكوى بحالة `closed`، ثم:
1. **إعادة تأكيد الهوية**: يُدخل الموقّع رمز TOTP الحالي (وليس PIN ثابت).
2. توقيع تشفيري حقيقي: مفتاح RSA-2048 خاص بالنظام (يُولَّد مرة واحدة، يُخزَّن في وحدة تخزين دائمة)، يوقّع نصًا مُركَّبًا من رقم الشكوى/الحالة/الموقّع/الوقت عبر **RSA-PSS/SHA-384**.
3. يُخزَّن في `digital_signatures`: التوقيع، بصمة الشهادة (SHA-256 للمفتاح العام)، هوية الموقّع، الوقت.

## ٩. سجلات النشاط المحصّنة (Tamper-Evident Logs)

جدولا `complaint_logs` (لكل شكوى) و`activity_logs` (نظام عام: دخول، مستخدمون، إدارات، تقارير):
- **سلسلة تجزئة**: كل سطر يحمل `row_hash = sha256(prev_hash + بيانات السطر)`.
- **Trigger في قاعدة البيانات** يرفض أي `UPDATE` أو `DELETE` على هذين الجدولين — تم اختباره حيًّا: محاولة `UPDATE`/`DELETE` مباشرة عبر psql تُرفض بخطأ `append-only`، حتى من مالك الجدول.
- الجدول القديم `audit_logs` (المصمَّم مسبقًا لكن غير المُستخدَم أبدًا) أُزيل نهائيًا؛ هذان الجدولان هما المرجع الوحيد الآن.
