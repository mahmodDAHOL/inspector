## ١. ما هو التطبيق؟

بوابة إلكترونية داخلية لمديرية الرقابة والتفتيش لإدارة **شكاوى الفساد والمخالفات الإدارية**: استقبال الشكوى، تحقيقها، تصعيدها عند الحاجة، إغلاقها، وتوقيع تقريرها النهائي — مع لوحة تحكم للمدير لإدارة المستخدمين والإدارات، وتقارير إحصائية، وسجل تدقيق (Audit Log) لكل ما يحدث في النظام.

## ٢. المكوّنات الرئيسية (Components)

النظام مبني على ٥ خدمات تعمل كحاويات Docker منفصلة (`docker-compose.yml`):

| الخدمة | الدور | ملاحظات |
|---|---|---|
| `nginx` | البوابة الأمامية، تشفير TLS (HTTPS)، توجيه الطلبات | المنفذ ٤٤٣ (HTTPS) و٨٠ (تحويل تلقائي إلى HTTPS) |
| `frontend` | تطبيق الواجهة (Vue 3) — يُبنى Build ثابت ويُقدَّم عبر nginx داخلي | لا يحتوي منطق أعمال، فقط واجهة |
| `backend` | واجهة برمجية (FastAPI) تحوي كل منطق الأعمال | ٤ عمليات Uvicorn Workers |
| `db` | قاعدة بيانات PostgreSQL 16 | تخزين كل البيانات |
| `redis` | Redis 7 | **مُجهَّز في البنية التحتية لكنه غير مُستخدم فعليًا في الكود حاليًا** (لا يوجد أي استدعاء له في `backend/app`) — فرصة مستقبلية لتنفيذ Rate Limiting أو تخزين الجلسات |

### هيكلية الكود

```
backend/app/
  api/v1/        # نقاط النهاية (Routers): auth, complaints, users, departments, dashboard, reports, audit, external
  core/          # security.py (JWT/كلمات المرور/TOTP), encryption.py (تشفير الحقول), deps.py (المصادقة/الصلاحيات), config.py
  models/        # نماذج SQLAlchemy: User, Complaint, Department, ComplaintLog, ActivityLog
  db/session.py  # اتصال قاعدة البيانات (Async SQLAlchemy)
  main.py        # نقطة التشغيل وربط كل الـ Routers

frontend/src/
  views/         # الصفحات: Dashboard, Complaints, Reports, AdminPanel, AuditLog, Login, Landing
  components/    # AppLayout (القائمة الجانبية + الهيكل العام)، AppHeader، SimpleBarChart
  stores/        # Pinia stores (auth, complaints, users, departments, dashboard, reports, audit, theme)
  locales/       # ar.json / en.json — كل نصوص الواجهة ثنائية اللغة
  router.js      # حماية المسارات (تسجيل الدخول / الأدوار)
```

## ٤. المميزات الرئيسية (Features)

1. **إدارة الشكاوى** — إنشاء، عرض، فلترة، تفاصيل كل شكوى مع رقم مرجعي تلقائي (`INS-YYYY-NNNN`).
2. **سير عمل الشكوى (Workflow)** — آلة حالة محددة بدقة، انظر القسم ٦.
3. **التعيين والتصعيد** — تعيين شكوى لمفتش، وتصعيدها إلى أولوية عاجلة.
4. **الملاحظات التحقيقية** — ملاحظات مرتبطة بكل شكوى، مع خيار "سرّي" (وضع علامة فقط — راجع تقرير الثغرات).
5. **التوقيع الرقمي للتقرير** — إجراء شكلي حاليًا يتطلب رمز PIN (راجع تقرير الثغرات — الرمز ثابت "1234" ولا يُخزَّن توقيع فعلي).
6. **سجل نشاط لكل شكوى (Complaint Activity Log)** — كل إجراء (إنشاء/تغيير حالة/تعيين/تصعيد/ملاحظة/توقيع) يُسجَّل تلقائيًا مع اسم من قام به والوقت، ويظهر كخط زمني (Timeline) في صفحة تفاصيل الشكوى.
7. **سجل تدقيق شامل للنظام (System Audit Log)** — صفحة "سجل التدقيق" تعرض كل نشاط في النظام (تسجيل دخول ناجح/فاشل، قفل حساب، إنشاء/تعديل مستخدم أو إدارة، توليد تقرير) بالإضافة إلى نشاط الشكاوى، مع فلاتر وترقيم صفحات.
8. **لوحة تحكم (Dashboard)** — إحصائيات حيّة: إجمالي الشكاوى، الحالات، الأولويات، الفئات، بالإضافة إلى **مؤشرات زمن الاستجابة** (نسبة الاستجابة، متوسط وقت أول استجابة بالساعات، عدد الشكاوى بانتظار استجابة).
9. **التقارير** — توليد تقرير ملخص ضمن مدى زمني محدد، مع تنزيله كملف JSON.
10. **لوحة التحكم الإدارية (Control Panel)** — أربع تبويبات: المستخدمون (CRUD)، الأدوار والصلاحيات (عرض مرجعي)، الإدارات (CRUD)، نظرة عامة على النظام (حالة الـ API والإحصائيات).
11. **مصادقة ثنائية العامل (MFA)** — انظر القسم ٧.
12. **قفل الحساب التلقائي** — بعد ٥ محاولات دخول فاشلة يُقفل الحساب ١٥ دقيقة.
13. **دعم لغتين وواجهة RTL/LTR** — تبديل فوري بين العربية والإنجليزية، مع تخزين التفضيل محليًا.
14. **الوضع الداكن/الفاتح** — يتبع تفضيل المستخدم.
15. **قائمة جانبية موحدة** — نفس القائمة والهيكل في كل صفحات النظام بعد تسجيل الدخول.

## ٥. آلية العمل العامة (Request Flow)

```
المتصفح ──HTTPS(443)──> nginx ──┬── "/"      ──> frontend (ملفات ثابتة مبنية بـ Vite)
                                 └── "/api/"  ──> backend (FastAPI على المنفذ 8000)

عند كل طلب API:
  axios (الواجهة) يرفق Authorization: Bearer <access_token> تلقائيًا (من localStorage)
       │
       ▼
  FastAPI dependency: get_current_user
       - يفك تشفير الـ JWT (HS256) ويتحقق من صلاحيته ونوعه ("access")
       - يجلب المستخدم من قاعدة البيانات ويتأكد أنه نشط (is_active)
       - عند الفشل → 401 Unauthorized
       │
       ▼
  (لبعض المسارات) require_roles("admin", "super_admin")
       - يتحقق أن دور المستخدم ضمن القائمة المسموحة
       - عند الفشل → 403 Forbidden
       │
       ▼
  منطق المسار (Route) ← SQLAlchemy AsyncSession ← PostgreSQL
```

المسارات المحمية بأدوار محددة حاليًا: إنشاء/تعديل/تعطيل مستخدم، وإنشاء/تعديل إدارة (`admin` أو `super_admin` فقط). بقية مسارات الشكاوى/التقارير/اللوحة متاحة لأي مستخدم مسجّل دخول بغض النظر عن دوره (راجع تقرير الثغرات، البند الخاص بضبط الصلاحيات).

## ٦. سير عمل الشكوى (Complaint Workflow / State Machine)

```
                 ┌──────────────┐
      إنشاء ──> │   received   │
                 └──────┬───────┘
                        │
            ┌───────────┼───────────────┐
            ▼           ▼               ▼
  under_investigation  closed      (لا يوجد انتقال مباشر لـ escalated من هنا عبر /status
                                    لكن endpoint منفصل /escalate يفعل ذلك مباشرة)
            │
   ┌────────┼─────────────┐
   ▼        ▼              ▼
received  escalated      closed
            │
     ┌──────┼──────┐
     ▼             ▼
under_investigation  closed

closed → (نهائي، لا انتقالات أخرى عبر /status)
```

- الانتقالات مضبوطة بجدول صريح في `complaints.py` (`VALID_STATUS_TRANSITIONS`) ويُرفض أي انتقال غير مسموح بخطأ `400`.
- `/complaints/{id}/escalate` إجراء خاص يغيّر الحالة إلى `escalated` والأولوية إلى `urgent` معًا، ومسموح فقط من `received` أو `under_investigation`.
- أول إجراء فعلي على الشكوى (تغيير حالة، تعيين، أو إضافة ملاحظة) يسجَّل تلقائيًا كـ "أول استجابة" (`first_response_at`) وهو الأساس الذي تُحسب عليه مؤشرات زمن الاستجابة في اللوحة والتقارير.
- كل انتقال/تعيين/تصعيد/ملاحظة/توقيع يُنشئ سطرًا في **سجل نشاط الشكوى** تلقائيًا.

## ٧. تسجيل الدخول ورمز التحقق (Login & MFA)

تسجيل الدخول يتم على **خطوتين إجباريتين**:

### الخطوة ١ — اسم المستخدم وكلمة المرور
`POST /api/v1/auth/login`
- يتحقق من: هل الحساب موجود؟ هل هو نشط (`is_active`)؟ هل هو مقفل حاليًا (`locked_until`)؟
- كلمة المرور تُقارَن عبر **Argon2** (خوارزمية اشتقاق مفتاح مقاومة لهجمات القوة الغاشمة وGPU).
- عند الفشل: يزداد عدّاد `failed_login_attempts`، وعند الوصول لـ ٥ محاولات يُقفل الحساب تلقائيًا لمدة **١٥ دقيقة** (`locked_until`).
- عند النجاح: يُصفَّر العدّاد، ويُصدَر **`temp_token`** (صالح ٥ دقائق فقط، `type: temp`) — لا يمنح أي صلاحية وصول، فقط يُثبت اجتياز الخطوة الأولى.

### الخطوة ٢ — رمز التحقق (TOTP)
`POST /api/v1/auth/verify-totp`
- يُدخل المستخدم رمزًا مكوّنًا من ٦ أرقام من تطبيق مصادقة (مثل Google Authenticator) يتغيّر كل ٣٠ ثانية، حسب معيار **TOTP (RFC 6238)** عبر مكتبة `pyotp`.
- سرّ TOTP الخاص بكل مستخدم (`totp_secret`) **مُخزَّن مشفّرًا** في قاعدة البيانات (وليس نصًا صريحًا) ويُفك تشفيره لحظة التحقق فقط.
- عند النجاح: يُصدَر **`access_token`** (صالح ١٥ دقيقة، يحمل `role` المستخدم) و**`refresh_token`** (صالح ٧ أيام)، ويُحدَّث `last_login_at`.
- بيانات المستخدم (`user`) تُخزَّن في `localStorage` في المتصفح — هي المرجع الذي تعتمد عليه القائمة الجانبية ولوحة التحكم لإظهار/إخفاء الروابط حسب الدور.

### كيف يتم توليد سرّ TOTP لمستخدم جديد؟
عند إنشاء مستخدم، يُولَّد سرّ عشوائي (`generate_totp_secret`) ويُشفَّر ويُخزَّن. سكربت `seed_demo.py` يطبع رمز TOTP الحالي لكل مستخدم تجريبي عند التشغيل (صالح ٣٠ ثانية فقط) لتسهيل تسجيل الدخول في بيئة التطوير.

### الرموز (Tokens) — ملخص
| الرمز | الصلاحية | الغرض |
|---|---|---|
| `temp_token` | ٥ دقائق | إثبات اجتياز خطوة كلمة المرور فقط |
| `access_token` | ١٥ دقيقة | الوصول الفعلي لكل الـ API (`Authorization: Bearer`) |
| `refresh_token` | ٧ أيام | تجديد `access_token` (ملاحظة: هذا المسار غير مُستخدم فعليًا من الواجهة حاليًا) |

كل الرموز موقّعة بـ **JWT/HS256** بمفتاح سري واحد (`SECRET_KEY`)، والتحقق من فك التشفير يقيّد الخوارزمية صراحةً إلى `HS256` (يمنع هجمات خلط الخوارزميات).

## ٨. الأدوار (Roles)

الأدوار الخمسة المعرَّفة في النظام:

| الدور | الوصف المعروض في الواجهة |
|---|---|
| `super_admin` | صلاحية كاملة على النظام |
| `admin` | إدارة المستخدمين، الإدارات، التقارير، الشكاوى |
| `senior_inspector` | تعيين الشكاوى، توقيع التقارير، إدارة التحقيقات |
| `inspector` | عرض الشكاوى، إضافة ملاحظات، تحديث الحالة |
| `viewer` | وصول للقراءة فقط |

**ملاحظة مهمة:** الأدوار مُعرَّفة ومعروضة في الواجهة، لكن **إنفاذها الفعلي على مستوى الخادم مطبَّق فقط على مسارات المستخدمين والإدارات** (`admin`/`super_admin`). مسارات الشكاوى مفتوحة لأي مستخدم مسجَّل دخول بغض النظر عن دوره — هذا موثّق بالتفصيل مع الحل المقترح في `security_audit_report_ar.md`.

## ٩. قاعدة البيانات — نظرة سريعة

جدول كامل بالأعمدة وطريقة الوصول موجود في `database_encryption_access_ar.md`. ملخص الجداول:

| الجدول | الغرض | الحالة |
|---|---|---|
| `departments` | الإدارات التنظيمية | مُستخدَم فعليًا |
| `users` | المستخدمون، بما فيها أعمدة قفل الحساب | مُستخدَم فعليًا |
| `complaints` | الشكاوى وكل بياناتها | مُستخدَم فعليًا |
| `investigation_notes` | ملاحظات التحقيق | مُستخدَم فعليًا |
| `complaint_logs` | سجل نشاط كل شكوى | مُستخدَم فعليًا (جديد) |
| `activity_logs` | سجل نشاط النظام العام (دخول، مستخدمون، إدارات، تقارير) | مُستخدَم فعليًا (جديد) |
| `audit_logs` | جدول تدقيق عام مُصمَّم مسبقًا (قيم قديمة/جديدة مشفّرة) | **موجود في قاعدة البيانات لكن غير مُستخدَم من أي مسار حاليًا** (كود `AuditLogger` غير متوافق تقنيًا مع بقية النظام) |
| `digital_signatures` | تخزين التواقيع الرقمية | **موجود لكن لا يُكتب فيه أي شيء فعليًا** — التوقيع حاليًا شكلي فقط |
| `alembic_version` | تتبّع نسخة مخطط قاعدة البيانات | تقني بحت |
