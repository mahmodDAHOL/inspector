## 🔴 حرجة — الكل مُصلَح

### C0 — (اكتُشفت أثناء الإصلاح) تجاوز كامل للمصادقة الثنائية (MFA Bypass)
**لم تكن في الفحص الأول.** دالة مسار `POST /auth/verify-totp` كانت مُسمّاة `verify_totp` — بنفس اسم الدالة المستوردة من `app.core.security` التي يفترض أن تتحقق من الرمز. هذا "حجب" (Shadowing) الدالة المستوردة داخل نطاق الوحدة (module)، فأصبح استدعاء `verify_totp(...)` داخل الدالة يستدعي **نفسه** كـ coroutine غير مُنتظَر (Never Awaited) — وهو ما يُقيَّم دائمًا كقيمة صحيحة (Truthy)، أي أن شرط الرفض `if not verify_totp(...)` **لم يكن يتحقق من صحة الرمز إطلاقًا**.

**التحقق (قبل الإصلاح):**
```
POST /auth/verify-totp {"temp_token": "...", "totp_code": "000000"}  →  200 OK + access_token صالح!
```
**الأثر:** أي شخص يعرف اسم مستخدم وكلمة مرور صحيحين (أو يخمّنهما) يتجاوز طبقة المصادقة الثانية بالكامل بإدخال أي ٦ أرقام.

**الإصلاح:** إعادة تسمية دالة المسار إلى `verify_totp_step` (مسار الـ URL نفسه لم يتغيّر). **تم التحقق بعد الإصلاح:** رمز خاطئ ← `401`، رمز صحيح ← `200` كما يجب. اكتُشفت هذه الثغرة بفضل اختبار pytest جديد (`test_login_flow.py`) — أفضل دليل على قيمة بند "لا اختبارات آلية" في الفحص الأصلي.

### C1 — أسرار النظام كانت مرفوعة إلى Git ✅ مُصلَح
**كان:** `.env` (SECRET_KEY، MASTER_ENCRYPTION_KEY، كلمتا مرور DB/Redis) ومفتاح TLS الخاص مضافان لتاريخ Git، بلا `.gitignore`.
**الإصلاح المطبَّق والمُتحقَّق منه:**
1. أُضيف `.gitignore` + `.env.example`.
2. أُزيلا من **كل الالتزامات (Commits)** عبر `git filter-branch --index-filter` ثم `git gc --prune=now` — تم التحقق: `git rev-list --objects --all | grep -i ".env$\|inspection-portal.key$"` لا يُرجع شيئًا.
3. **دُوِّرت كل القيم فعليًا** على النظام الحي: `SECRET_KEY`, `MASTER_ENCRYPTION_KEY` (وأُعيد بذر البيانات التجريبية تحت المفتاح الجديد)، كلمة مرور DB (عبر `ALTER USER` حي)، كلمة مرور Redis، شهادة TLS جديدة (صالحة حتى ٢٠٢٨).
4. **تم التحقق حيًّا** بعد كل تدوير: تسجيل الدخول، فك تشفير حقل، واتصال الخلفية بقاعدة البيانات — كلها تعمل بالقيم الجديدة.

### C2 — نقاط تكامل MediaGate بلا مصادقة فعلية ✅ مُصلَح
**كان:** أي طلب يُقبل بلا أي مفتاح أو توقيع.
**الإصلاح:** تحقق فعلي من `X-API-Key` (مقارنة بقيمة `MEDIAGATE_API_KEY`)، وتوقيع `X-Signature` (HMAC-SHA256 على جسم الطلب)، + تحديد معدل ٣٠ طلب/دقيقة لكل IP.
**التحقق الحي:** بلا مفتاح ← `401`. مفتاح صحيح + توقيع خاطئ ← `401`. مفتاح وتوقيع صحيحان ← `200`. تجاوز ٣٠ طلب/دقيقة ← `429` (تم تفعيل الحد فعليًا وملاحظته في السجل).

### C3 — "التوقيع الرقمي" كان شكليًا بالكامل ✅ مُصلَح
**كان:** PIN ثابت "1234" للجميع، لا توقيع حقيقي، لا كتابة في `digital_signatures`.
**الإصلاح:** توقيع RSA-PSS/SHA-384 حقيقي بمفتاح ٢٠٤٨-بت خاص بالنظام (`app/core/signing.py`)، مع **إعادة تأكيد الهوية عبر رمز TOTP الحالي للموقّع** بدل PIN مشترك، وتقييد الإجراء لأدوار `senior_inspector` فما فوق فقط.
**التحقق الحي:** توقيع بدور خاطئ ← `403`. توقيع برمز TOTP خاطئ ← `401`. توقيع صحيح ← توقيع RSA حقيقي مُرجَع + سطر فعلي في `digital_signatures` (تم التحقق بالاستعلام المباشر).

## 🟠 عالية — الكل مُصلَح

| # | كان | الإصلاح | التحقق الحي |
|---|---|---|---|
| H1 | الأدوار غير مُنفَّذة على الشكاوى؛ `viewer` يستطيع الكتابة فعليًا | `require_roles` مطبَّق حسب مصفوفة دقيقة (إنشاء/تعديل: كل الأدوار عدا viewer؛ توقيع: senior_inspector+) | `viewer` ينشئ شكوى ← `403`. يقرأ ← `200` |
| H2 | علامة "سرّي" على الملاحظات شكلية | فلترة فعلية: يراها فقط `senior_inspector`+ أو كاتبها | مستخدم `viewer` يرى `content: null, hidden: true` |
| H3 | `CORS allow_origins=["*"]` مع `allow_credentials=True` | قائمة أصول صريحة عبر `ALLOWED_ORIGINS` في `.env` | — |
| H4 | `TrustedHostMiddleware(allowed_hosts=["*"])` | قائمة نطاقات صريحة عبر `ALLOWED_HOSTS` | اختبار pytest بـ `Host: test` غير مسموح ← `400` فعليًا (اكتُشف أثناء كتابة الاختبارات) |
| H5 | لا حد أدنى لقوة كلمة المرور — كلمة مرور فارغة تُقبل | تحقق Pydantic: ١٠ أحرف على الأقل + ٣ من ٤ أصناف أحرف | كلمة مرور فارغة ← `422`. كلمة قوية ← `201` |
| H6 | أسرار افتراضية ضعيفة (`"dev-secret-key"`) كـ Fallback | `SECRET_KEY`/`MASTER_ENCRYPTION_KEY` بلا قيمة افتراضية؛ يرفض الإقلاع إن كانت مفقودة/ضعيفة | تحقق Pydantic فعلي عند الإقلاع |

## 🟡 متوسطة — الكل مُصلَح

| # | كان | الإصلاح |

| M7 | لا اختبارات آلية | ٢٢ اختبار pytest (وحدة: تشفير، كلمات مرور/TOTP، آلة حالة الشكوى؛ تكامل: تدفق الدخول الكامل) — **وهي التي اكتشفت الثغرة C0** |

## ملاحظات متبقية (منخفضة الخطورة، للعلم وليس للتنفيذ الفوري)

هذه لم تكن أخطاء يجب إصلاحها بالضرورة، بل حدود معروفة في التصميم الحالي يجدر توثيقها بأمانة:

1. **`TRUNCATE` يتجاوز حماية سجلات النشاط.** الـ Trigger يعترض `UPDATE`/`DELETE` فقط (سلوك قياسي في PostgreSQL — المشغّلات على مستوى السطر لا تُفعَّل مع `TRUNCATE`). هذا مقصود جزئيًا (يسمح لـ `seed_demo.py` بمسح البيانات التجريبية)، لكنه يعني أن من يملك وصولاً مباشرًا لقاعدة البيانات (أصلاً وضع يتجاوز التطبيق بالكامل) يستطيع مسح السجلات دفعة واحدة. إن أُريد إغلاق هذه الثغرة نهائيًا: مشغّل إضافي `BEFORE TRUNCATE`، مع استثناء صريح لسكربتات الصيانة.
2. **مفتاح توقيع واحد للنظام بأكمله**، وليس شهادة لكل موقّع صادرة عن جهة تصديق (CA) معترف بها. مقبول لبيئة العمل الداخلية الحالية؛ لأي قيمة قانونية/إثباتية رسمية للتوقيع مستقبلاً، يلزم PKI حقيقي بشهادات فردية.
3. **`MEDIAGATE_API_KEY` الحالي قيمة عشوائية مولَّدة لبيئة التطوير**، وليس مفتاحًا حقيقيًا من MediaGate — استبدله عند التكامل الفعلي.
4. **لا آلية استرداد لحساب فقد صاحبه جهاز TOTP.** حاليًا لا يوجد مسار لإعادة تعيين سرّ TOTP لمستخدم غير قادر على الدخول سوى تدخل يدوي مباشر في قاعدة البيانات من `super_admin`. يُستحسن إضافة نقطة نهاية إدارية (`admin`/`super_admin` فقط) لإعادة توليد سرّ TOTP لمستخدم محدد، مع تسجيل الإجراء في سجل النشاط.
5. **لا سياسة انتهاء صلاحية لكلمة المرور ولا إعادة تعيين ذاتية (Self-Service Password Reset).** خارج نطاق هذه الجولة من الإصلاحات.
6. **الشهادة الجديدة لا تزال ذاتية التوقيع (Self-Signed).** مناسبة للتطوير المحلي؛ يلزم استبدالها بشهادة صادرة عن جهة تصديق معترف بها (مثل Let's Encrypt) قبل أي نشر حقيقي على نطاق عام.
