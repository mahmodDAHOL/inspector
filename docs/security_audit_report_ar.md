## 🔴 حرجة (Critical)

### C1 — أسرار النظام كاملة مرفوعة إلى Git، بلا `.gitignore` إطلاقًا
**الوصف:** ملف `.env` (يحوي `SECRET_KEY` الخاص بتوقيع JWT، `MASTER_ENCRYPTION_KEY` الخاص بتشفير كل الحقول الحسّاسة، كلمتي مرور قاعدة البيانات وRedis) **مضاف فعليًا لتاريخ Git** (`git ls-files` يُظهره). كذلك المفتاح الخاص لشهادة TLS: `ssl/inspection-portal.key`. **لا يوجد ملف `.gitignore` في المشروع بالكامل.**

**التحقق:**
```
$ git ls-files | grep -iE "\.env$|\.key$"
.env
ssl/inspection-portal.key
```

**الأثر:** أي شخص يحصل على نسخة من المستودع (حتى نسخة قديمة من التاريخ، حتى لو حُذف الملف لاحقًا) يملك مفاتيح فك تشفير كل البيانات الحسّاسة في قاعدة البيانات، ومفتاح توقيع جلسات الدخول (يمكنه تزوير جلسة دخول كاملة لأي مستخدم بمعرفة `user_id` فقط)، ومفتاح TLS الخاص.

**الحل المقترح:**
1. أنشئ `.gitignore` فورًا يحوي `.env`, `*.key`, `ssl/*.key`.
2. أزل هذه الملفات من تاريخ Git بالكامل (`git filter-repo` أو `BFG Repo-Cleaner`)، وليس فقط بحذفها في Commit جديد.
3. **دوّر (Rotate)** كل القيم: `SECRET_KEY`, `MASTER_ENCRYPTION_KEY`, كلمتي مرور DB/Redis، وأصدر شهادة TLS جديدة — لأن القيم الحالية يجب اعتبارها "محروقة" بمجرد ظهورها في التاريخ ولو مرة.
4. وزّع القيم الحقيقية لاحقًا عبر آلية أسرار خارج Git (`.env` محلي غير مرفوع + متغيرات بيئة في الاستضافة، أو Vault/Secrets Manager).

### C2 — نقاط نهاية تكامل MediaGate الخارجية بلا أي مصادقة فعلية
**الوصف:** `backend/app/api/v1/external.py` يستقبل ترويسات `X-API-Key` و`X-Signature` كمعاملات، **لكن لا يتحقق من قيمتيهما إطلاقًا** — أي طلب، بأي قيمة (أو بدون الترويسات نهائيًا)، يُقبل وينفَّذ.

**التحقق (مباشرة على النظام الحي، بلا أي مفتاح):**
```
$ curl -sk https://localhost/api/v1/external/poll/complaints
{"complaints":[{...}],"pagination":{...}}   ← نجح بدون أي مفتاح

$ curl -sk -X POST https://localhost/api/v1/external/push/status -d '{...}'
{"message":"Status pushed successfully",...}   ← نجح بدون أي توقيع
```

**الأثر:** أي شخص يصل إلى عنوان الخادم (وهو معروض على الإنترنت عبر nginx) يمكنه دفع تحديثات حالة مزيّفة لأي شكوى، أو استعلام حالة أي شكوى برقمها، دون أي حساب أو صلاحية.

**الحل المقترح:**
1. أضف تحققًا فعليًا: قارن `X-API-Key` بقيمة `MEDIAGATE_API_KEY` من الإعدادات (موجودة أصلًا في `config.py` لكنها غير مُستخدَمة).
2. تحقق من `X-Signature` فعليًا (HMAC على جسم الطلب بمفتاح مشترك)، وارفض بـ `401` عند عدم التطابق.
3. أضف Rate Limiting مستقل على هذه المسارات لأنها موجّهة لخدمة خارجية آلية.

### C3 — "التوقيع الرقمي" شكلي بالكامل: PIN ثابت للجميع، ولا يُخزَّن أي توقيع فعلي
**الوصف:** `POST /complaints/{id}/sign` يقارن الـ PIN المُدخل بقيمة ثابتة `"1234"` مكتوبة في الكود مباشرة، متطابقة لكل المستخدمين، بلا علاقة بأي مفتاح توقيع حقيقي. الاستجابة تدّعي خوارزمية `"RSA-PSS-SHA384"` لكن **لا يوجد أي كود يُنشئ توقيعًا رقميًا حقيقيًا**، وجدول `digital_signatures` المُعَدّ لهذا الغرض **لا يُكتب فيه أي سطر أبدًا**.

**الأثر:** أي موظف — بغض النظر عن هويته أو صلاحيته — يعرف الرقم "1234" (وهو مكتوب بوضوح في الواجهة كـ "الرمز التجريبي") يمكنه "توقيع" أي تقرير مغلق. هذا يبطل أي قيمة قانونية/إثباتية للتوقيع، وهو أمر حسّاس في نظام رقابة وتفتيش حكومي.

**الحل المقترح:**
1. اربط توقيع التقرير برمز PIN **خاص بكل مستخدم** (مثلاً هاش Argon2 منفصل يُنشأ عند أول استخدام)، أو استبدله بإعادة طلب كلمة المرور/TOTP كتأكيد هوية (Re-authentication) بدلًا من رقم ثابت منفصل.
2. نفّذ توقيعًا تشفيريًا حقيقيًا: زوج مفاتيح خاص بكل مُوقِّع (أو بالنظام)، وقّع هاش محتوى التقرير فعليًا (RSA-PSS أو Ed25519)، واحفظ التوقيع في `digital_signatures` مع بصمة الشهادة.
3. حتى يُنجَز ذلك، أزل الادّعاء بخوارزمية توقيع من الاستجابة لتجنّب إيحاء زائف بالأمان.

## 🟠 عالية (High)

### H1 — الأدوار غير مُنفَّذة فعليًا على وحدة الشكاوى
**الوصف:** كل نقاط نهاية الشكاوى (`complaints.py`) تتطلب فقط "أي مستخدم مسجّل دخول" (`get_current_user`)، بلا أي تحقق من الدور. هذا يعني أن دور `viewer` — الموصوف في الواجهة صراحةً بـ"وصول للقراءة فقط" — يستطيع فعليًا: إنشاء شكاوى، تغيير حالتها، تعيينها، تصعيدها، إضافة ملاحظات، بل وتوقيع التقارير.

**التحقق:** مراجعة كود مباشرة — `router = APIRouter(dependencies=[Depends(get_current_user)])` في `complaints.py` بلا أي `require_roles` على أي مسار كتابة.

**الحل المقترح:** أضف `require_roles(...)` المناسبة لكل إجراء حسّاس، بما يعكس فعليًا مصفوفة الصلاحيات المعروضة في لوحة التحكم:
- إنشاء شكوى: أي دور فيما عدا `viewer`.
- تغيير الحالة/التعيين/التصعيد: `inspector` فما فوق.
- التوقيع: `senior_inspector` فما فوق فقط (كما هو موصوف في الواجهة).
- `viewer`: قراءة فقط على كل هذه المسارات (رفض الطلبات الكاتبة بـ `403`).

### H2 — علامة "سرّي" على الملاحظات التحقيقية شكلية فقط
**الوصف:** `is_confidential` يُخزَّن ويُعرَض، لكن `GET /complaints/{id}/notes` يُرجع كل الملاحظات — السرّية وغير السرّية — لأي مستخدم يملك حق الوصول للشكوى نفسها، دون أي فلترة إضافية حسب الدور.

**الحل المقترح:** فلترة الملاحظات المُعلَّمة `is_confidential` لتكون مرئية فقط لدور `senior_inspector` فما فوق (أو لمن أنشأها + المدراء)، مع رسالة واضحة في الواجهة عند إخفاء ملاحظات سرّية عن المستخدم الحالي.

### H3 — تركيبة CORS خطرة: `allow_origins=["*"]` مع `allow_credentials=True`
**الوصف (مراجعة كود، `main.py`):** هذا التوليف مخالف لمواصفة CORS (المتصفحات يُفترض أن ترفضه)، لكنه يدل على إعداد غير مضبوط، وأي تعديل مستقبلي (مثل عكس الـ Origin المُرسَل بدل النجمة، وهو خطأ شائع) يفتح الباب لسرقة الجلسة عبر أي موقع خارجي.

**الحل المقترح:** حدد نطاق الأصول المسموحة صراحةً (`allow_origins=["https://your-real-domain"]`) بدل النجمة، خصوصًا مع تفعيل `allow_credentials`.

### H4 — `TrustedHostMiddleware` بإعداد `allowed_hosts=["*"]`
**الوصف:** يُبطل الغرض الكامل من الـ Middleware (منع هجمات Host Header) — وهو مطابق تمامًا لإعداد CORS المذكور أعلاه: موجود بالاسم لكن غير فعّال.

**الحل المقترح:** ضع أسماء النطاقات الحقيقية المتوقعة فقط.

### H5 — عدم وجود أي حد أدنى لقوة كلمة المرور
**التحقق (مباشرة على النظام):**
```
POST /api/v1/users  { "password": "" , ... }  →  201 Created (تم إنشاء المستخدم بكلمة مرور فارغة!)
```
**الحل المقترح:** أضف تحقق Pydantic (`min_length=10` على الأقل + تنويع أحرف) على `UserCreate.password`، وارفض القيم الفارغة أو الضعيفة على مستوى الـ Schema مباشرة (وليس فقط توثيقًا في الواجهة).

### H6 — أسرار افتراضية ضعيفة كـ Fallback في الكود
**الوصف (`config.py`):**
```python
SECRET_KEY: str = "dev-secret-key"
MASTER_ENCRYPTION_KEY: str = "dev-encryption-key"
```
إذا تعطّل تحميل `.env` لأي سبب (خطأ نشر، متغير بيئة مفقود)، **يبدأ النظام بمفاتيح معروفة للعامة بدل الفشل الآمن (Fail-Safe)**.

**الحل المقترح:** احذف القيم الافتراضية، واجعل التطبيق **يرفض الإقلاع** إن لم تكن `SECRET_KEY`/`MASTER_ENCRYPTION_KEY` معرَّفتين صراحةً (تحقق في `get_settings()` أو عبر `Field(...)` بلا default).

## 🟡 متوسطة (Medium)

### M1 — لا يوجد أي تحديد لعدد المحاولات (Rate Limiting) على مستوى الـ IP
عداد الفشل الحالي (٥ محاولات) مرتبط بالحساب فقط. مهاجم يملك قائمة أسماء مستخدمين يمكنه تجربة ٤ كلمات مرور لكل حساب من آلاف الحسابات دون أن يُقفَل أي منها (هجوم Credential Spraying). Redis مُجهَّز في البنية التحتية أصلًا وغير مُستخدَم — فرصة مثالية لتطبيق Rate Limiting عام (بحسب IP) على `/auth/login` و`/auth/verify-totp`.

### M2 — نظامان متنافسان لسجل التدقيق، أحدهما ميت
`app/core/audit.py` (`AuditLogger`) مكتوب لاتصال `asyncpg` خام بترميز `$1, $2...`، **غير متوافق مع بقية النظام** الذي يستخدم SQLAlchemy AsyncSession بترميز `:name` — ولذلك **لم يُستدعَ من أي مسار إطلاقًا**. جدول `audit_logs` (المصمَّم بتشفير القيم القديمة/الجديدة وتجزئة IP — وهو تصميم أدق خصوصية من الجداول الجديدة) فارغ دائمًا.

**الحل المقترح:** إما أعد كتابة `AuditLogger` ليعمل عبر `AsyncSession` وفعّل استدعاءه، أو احذفه رسميًا وثبّت `complaint_logs`/`activity_logs` كمرجع الوحيد، مع توثيق القرار.

### M3 — سجلات النشاط الجديدة غير محصّنة ضد التلاعب (Not Tamper-Evident)
`complaint_logs` و`activity_logs` جداول عادية قابلة للتعديل/الحذف من أي وصول مباشر لقاعدة البيانات، بلا تسلسل تجزئة (Hash Chain) أو صلاحية Append-Only على مستوى القاعدة. هذا مقبول كسجل تشغيلي، لكنه غير كافٍ إن كان الهدف "سجل تدقيق" بمعنى الامتثال (لا يمكن إثبات عدم العبث به لاحقًا).

**الحل المقترح:** لأغراض الامتثال الفعلي، أضف عمود `prev_hash`/`row_hash` (تسلسل تجزئة تراكمي) أو فعّل صلاحيات قاعدة بيانات تمنع `UPDATE`/`DELETE` على هذين الجدولين حتى لمالك القاعدة (Trigger يرفضهما).

### M4 — مسار `/auth/refresh` لا يقبل جسم JSON فعليًا (خلل تصميم يهدد بتسريب الرمز مستقبلًا)
**التحقق:**
```
POST /auth/refresh  Content-Type: json  {"refresh_token": "..."}   → 422 (يرفض!)
POST /auth/refresh?refresh_token=...                                → يُقبل (استعلام Query)
```
السبب: المعامل `refresh_token: str` غير مُغلَّف بـ `Body(...)` أو نموذج Pydantic، فتتعامل معه FastAPI افتراضيًا كمعامل استعلام. المسار غير مُستخدَم حاليًا من الواجهة، لكن أي تطوير مستقبلي "ساذج" لتفعيله سيضع رمز التجديد الحسّاس في رابط الطلب — يُسجَّل في سجلات الخادم/الوسيط ويظهر في تاريخ المتصفح.

**الحل المقترح:** غلّفه بنموذج Pydantic (`class RefreshRequest(BaseModel): refresh_token: str`) كبقية المسارات.

### M5 — `create_admin.py` غير فعّال فعليًا
يجمع اسم مستخدم وكلمة مرور، ثم **لا يكتب شيئًا في قاعدة البيانات** — فقط يطبع تعليمات. الطريقة الوحيدة العملية حاليًا لإنشاء أول مستخدم هي `seed_demo.py`، وهو **مدمِّر** (يحذف كل البيانات الموجودة قبل الإدخال) — غير مناسب على بيئة فيها بيانات حقيقية.

**الحل المقترح:** أكمل السكربت فعليًا (إدخال المستخدم عبر SQLAlchemy مباشرة، بلا حذف أي بيانات موجودة).

### M6 — لا رؤوس أمان حديثة (Security Headers) على مستوى nginx
الموجود حاليًا: `X-Frame-Options`, `X-Content-Type-Options`, `X-XSS-Protection` (هذا الأخير مهجور فعليًا في المتصفحات الحديثة). **لا يوجد** `Content-Security-Policy` ولا `Strict-Transport-Security` (HSTS) ولا `Referrer-Policy`.

**الحل المقترح:** أضف `Strict-Transport-Security: max-age=31536000; includeSubDomains` (البروتوكول HTTPS مُفعَّل أصلًا فلا كلفة إضافية)، و`Content-Security-Policy` تقيّد مصادر السكربتات (يخفف من أثر XSS المحتمل، وهو مهم بالذات لأن رمز الدخول مُخزَّن في `localStorage`).

### M7 — لا اختبارات آلية في المشروع
لا يوجد مجلد `tests/` لا في الخلفية ولا الواجهة. عدة أخطاء فعلية وُجدت وأُصلحت يدويًا في هذه الجولات (مثال: عدم حفظ بيانات المستخدم في `localStorage` مما كان يُخفي لوحة التحكم عن المدراء فعليًا) كان يمكن اكتشافها فورًا باختبار بسيط.

**الحل المقترح:** ابدأ بحد أدنى: اختبارات `pytest` لتدفق تسجيل الدخول وسير عمل الشكوى (الانتقالات المسموحة/الممنوعة)، واختبار وحدة لخدمة التشفير.

## ⚪ منخفضة / تحسينات (Low)

| # | الملاحظة | الاقتراح |
|---|---|---|
| L1 | `docs_url="/api/docs" if False else None"` في `main.py` | كود مربك (شرط ثابت دائمًا `False`) رغم أن النتيجة صحيحة أمنيًا (توثيق Swagger مُعطَّل) — بسّطه إلى `None` مباشرة لوضوح القصد. |
| L2 | إصدارات الاعتماديات مثبَّتة بدقة (`==`) بلا آلية تحديث دورية | أضف `pip-audit` و`npm audit` (أو Dependabot) في سير عمل CI للتنبيه عند ظهور ثغرات في الإصدارات المثبَّتة. |
| L3 | لا ترقيم صفحات (Pagination) على قوائم الشكاوى/المستخدمين | غير مؤثر عند ١٥ شكوى تجريبية، لكن سيصبح مشكلة أداء حقيقية مع نمو البيانات — أضف `limit`/`offset` قبل الإنتاج. |
